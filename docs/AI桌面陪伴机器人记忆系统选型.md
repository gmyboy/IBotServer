# AI 桌面陪伴机器人 · 记忆系统


## 一、记忆什么

1. 用户愿意把它当作**有性格的存在**，不是工具；
2. 用户愿意在「手机放下充电」时，每天跟它聊几句。

具体目标：

| 场景 | 用户感受 | PRD 对应 |
|---|---|---|
| 手机放回底座 | 「回来啦，刚说到你那个面试……」 | 唤醒衔接，最高 ROI 的留存钩子 |
| 隔几天再聊 | 「上次说的那事后来怎么样了？」 | 未完成话题回访 |
| 日常对话 | 「你叫小明吧？你不是不喜欢被打扰吗？」 | 记住名字、偏好、重要事件 |

## 二、记忆分层

```
┌─────────────────────────────────────────────────┐
│  L1 当前对话（Working Memory）                    │
│  本次聊天最近 10~20 轮，保证对话连贯               │
│  存储：Redis / 内存，会话结束可丢弃                 │
└─────────────────────────────────────────────────┘
                      ↓ 会话结束后异步写入
┌─────────────────────────────────────────────────┐
│  L2 用户记忆库（Long-term Memory）                 │
│  名字、偏好、重要事件、未完成话题                   │
│  存储：PostgreSQL，手机离位也不丢                   │
└─────────────────────────────────────────────────┘
```

### L2 记忆库的四类内容

| 类型 | 示例 | 用途 |
|---|---|---|
| **基础信息** | 名字、称呼、作息 | 日常对话个性化 |
| **偏好** | 喜欢聊运动、晚上别主动搭话 | 控制说话方式 |
| **重要事件** | 下周一有面试、女儿生日 | 后续关心 |
| **未完成话题** | 「上次说的项目延期那事」 | 隔几天主动回访 |

### 数据结构

```json
{
  "id": "mem_001",
  "user_id": "u_123",
  "type": "event",
  "content": "用户下周一有一场重要面试",
  "status": "open",
  "importance": 0.8,
  "created_at": "2026-06-01T10:00:00Z",
  "last_mentioned_at": "2026-06-01T10:00:00Z"
}
```

`status` 取值：

- `open`：未完成，可被主动回访
- `closed`：已解决，不再主动提
- `archived`：过期归档

## 三、一次对话流程

### 3.1 读：用户说话时

```
用户说话
  │
  ├─► 1. 读 L1：本次最近对话
  │
  ├─► 2. 读 L2：该用户的记忆库
  │       · 基础信息、偏好 → 全量注入（量小，通常 < 20 条）
  │       · 重要事件、未完成话题 → 按相关度取 Top 3~5
  │
  ├─► 3. 读情绪侧写（本地采集，云端存储）
  │       · 今天是否疲惫/烦躁 → 影响说话语气
  │
  ├─► 4. 拼装 Prompt → 调用 LLM → 流式返回 → TTS
  │
  └─► 5. 端侧播放 + 表情联动
```

**Prompt 拼装示例**：

```
[System: 默认人设 + 说话风格]

[用户记忆]
- 名字：小明
- 偏好：不喜欢晚上被打扰
- 未完成话题：下周一有重要面试（3天前提到）

[今日状态]
- 情绪侧写：今日多次显疲惫

[最近对话]
...最近 10 轮...

[用户输入]
"今天好累啊"
```

### 3.2 写：对话结束后（异步，不阻塞）

```
对话结束 / 每 5~10 轮
  │
  └─► 后台任务：LLM 从对话中抽取记忆
        │
        ├─► 新事实 → 写入 L2
        ├─► 旧事实有更新 → 覆盖或合并
        └─► 话题已解决 → status 改为 closed
```

**抽取示例**：

```
用户："我女儿小米下周三生日，她最爱草莓蛋糕"

↓ LLM 抽取（输出 JSON）

[
  {"type":"basic", "content":"用户女儿叫小米"},
  {"type":"event", "content":"女儿下周三生日，喜欢草莓蛋糕", "importance":0.9}
]
```

## 四、模块配合

```
┌─────────────── Android App ───────────────┐
│  感知（本地）    表达（本地+云端）          │
│  · 人脸/表情     · 表情动画               │
│  · 语音采集      · TTS 播放               │
│  · 唤醒词        · 躯壳动作指令            │
│                                           │
│  本地缓存         记忆中心 UI              │
│  · 最近对话       · 查看/编辑/删除记忆     │
└───────────────────┬───────────────────────┘
                    │ HTTPS / WebSocket
┌───────────────────▼───────────────────────┐
│              云端后端                       │
│  · 对话 API（ASR → LLM → TTS）            │
│  · 记忆读写 API                            │
│  · 异步记忆抽取任务                         │
│  · 主动搭话决策（读记忆 + 情绪 + 时间）    │
└───────────────────┬───────────────────────┘
                    │
         ┌──────────┴──────────┐
         │  PostgreSQL          │
         │  · 用户记忆库 (L2)   │
         │  · 情绪侧写          │
         │  · 提醒/节律配置     │
         └─────────────────────┘
```

### 前后端

| 功能 | Android | 云端 |
|---|---|---|
| 语音对话 | 采集音频、播放 TTS | ASR、LLM、TTS |
| 表情/情绪 | 本地推理（不上传原图） | 只收情绪标签 |
| 记忆存储 | 不存权威数据 | PostgreSQL 为唯一权威 |
| 记忆展示 | 记忆中心 UI | 提供 CRUD API |
| 唤醒衔接 | 检测手机回位 | 返回最近记忆用于问候 |
| 主动回访 | 接收推送/轮询 | 决策引擎读记忆库 |

**原则**：记忆权威在云端，手机只是「临时接入的大脑」，拿走手机记忆不丢。

## 五、方案与选型

### 5.1 记忆实现方案对比

| 方案 | 做法 | 可行性 | 接入难度 | 智能化 | 存储 | 协议 | 商业化 |
|---|---|---|---|---|---|---|---|
| **A. 结构化记忆库（推荐）** | PG 存 JSON 记忆条目，LLM 抽取写入 | ★★★★★ | ★★★★★ 最简单 | ★★★★ 够用 | 极小（< 1MB/用户/年） | PG 协议 ✅ | ✅ |
| **B. Mem0 开源框架** | 封装好的记忆 SDK | ★★★★ | ★★★★ pip 即用 | ★★★★ | 中等 | Apache 2.0 ✅ | ✅ |
| **C. 纯 Prompt 摘要** | 每次把历史摘要塞进 Prompt | ★★★ | ★★★★★ | ★★★ | 小 | — | ✅ |
| **D. 向量检索 + RAG** | Embedding + 向量库语义召回 | ★★★★ | ★★★ 需部署向量库 | ★★★★★ | 较大 | 视组件 | ✅ |
| **E. ChatGPT Memory API** | 直接用 OpenAI 记忆 | ★★ | ★★★★★ | ★★★ | — | 闭源 ❌ | ❌ 不可二次分发 |

**第一期推荐：方案 A（结构化记忆库）**

理由：
- PRD 的记忆类型本身就是结构化的（名字、偏好、事件、未完成话题）；
- 单用户记忆量小（几十到几百条），不需要向量检索；
- 开发量最小，2~3 周可上线；
- 完全自主可控，支持商业化。

**第二期再考虑**：当记忆条目 > 500 条、或需要「语义模糊召回」时，再加 pgvector / Qdrant（方案 D）。

### 5.2 存储方案对比

| 方案 | 组件 | 接入难度 | 性能 | 单用户存储/年 | 协议 | 推荐 |
|---|---|---|---|---|---|---|
| **PostgreSQL** | 单库搞定 | ★★★★★ | ★★★★★ | < 1 MB | PostgreSQL ✅ | **✅ 第一期** |
| PostgreSQL + pgvector | PG 加向量扩展 | ★★★★ | ★★★★ | 10~50 MB | PostgreSQL ✅ | 第二期 |
| Qdrant 向量库 | 独立向量服务 | ★★★ | ★★★★★ | 50~500 MB | Apache 2.0 ✅ | 第二期 |
| MongoDB | 文档库 | ★★★★ | ★★★★ | 中等 | SSPL ⚠️ | 不推荐 |
| Redis 持久化 | 内存数据库 | ★★★★★ | ★★★★★ | 小 | BSD ✅ | 仅做 L1 会话 |

### 5.3 LLM 方案对比

| 方案 | 成本 | 中文能力 | 延迟 | 协议 | 推荐 |
|---|---|---|---|---|---|
| **DeepSeek-V4 API** | **0.025元**/百万 token(未命中) **3元**/百万 token(命中) | ★★★★★ | ~400ms | MIT ✅ | **✅ 对话+抽取** |
| Qwen2.5-72B 自托管 | ~¥2/百万 token | ★★★★★ | ~500ms | Apache 2.0 ✅ | 备选 |
| GPT-4o API | ~¥70/百万 token | ★★★★ | ~800ms | 闭源 | 不推荐第一期 |
| Qwen2.5-7B 自托管 | 极低 | ★★★★ | ~200ms | Apache 2.0 ✅ | **✅ 记忆抽取** |

**第一期策略**：
- 对话生成：DeepSeek-V4 或 Qwen API（一个供应商即可，不需要 Router）；
- 记忆抽取：Qwen2.5-7B 或 DeepSeek（小模型够用，成本极低）；
- 不需要 LangGraph / Temporal，用简单的后台任务队列（Celery / Bull / 定时 Job）即可。

### 5.4 向量检索要不要上？

| 场景 | 需不需要向量检索 | 原因 |
|---|---|---|
| 记忆 < 200 条 | **不需要** | 全量注入 Prompt 即可，LLM 自己选 |
| 记忆 200~500 条 | 可选 | 按 type + importance 筛选后注入 |
| 记忆 > 500 条 | 需要 | 全量注入会超 Token 窗口 |
| 需要「模糊语义召回」 | 需要 | 如「上次聊的那个工作的事」 |

**第一期结论：不上向量检索。** PRD 的记忆类型明确、条目有限，结构化查询 + 全量/筛选注入完全够用。

## 六、推荐技术栈（第一期）

### 6.1 最简可用栈

| 层级 | 选型 | 协议 | 说明 |
|---|---|---|---|
| **Android** | Kotlin + Compose | Apache 2.0 | 对话 UI + 记忆中心 |
| **Android 缓存** | Room（最近对话） | Apache 2.0 | 离线回看，非权威 |
| **API 网关** | FastAPI（Python）或 NestJS（Node） | MIT | 语言不限，选团队熟悉的 |
| **数据库** | PostgreSQL 16 | PostgreSQL ✅ | 记忆库 + 情绪侧写 + 提醒 |
| **会话缓存** | Redis（可选） | BSD ✅ | L1 当前对话，可先用内存替代 |
| **异步任务** | Celery / APScheduler / Bull | 各 MIT | 记忆抽取，不需要 Temporal |
| **LLM 对话** | DeepSeek-V3 API | MIT ✅ | 一个 API 搞定 |
| **LLM 抽取** | Qwen2.5-7B 或 DeepSeek | Apache 2.0 / MIT ✅ | 异步抽取记忆 |
| **ASR** | 阿里云 / 讯飞 / SenseVoice | 各不同 | 选成熟 API 或开源 |
| **TTS** | 阿里云 / CosyVoice2 | Apache 2.0 ✅ | 情绪化语调 |

### 6.2 存储估算

| 数据 | 单用户/年 | 1 万用户 |
|---|---|---|
| 记忆条目（~200 条） | ~100 KB | ~1 GB |
| 情绪侧写（~365 天） | ~50 KB | ~500 MB |
| 提醒/节律配置 | ~10 KB | ~100 MB |
| 对话日志（可选） | ~5 MB | ~50 GB |
| **合计** | **~5 MB** | **~50 GB** |

对比之前四层方案的 150MB~5GB/用户，第一期存储需求**小两个数量级**。

### 6.3 成本估算

| 项目 | 单用户/月 | 1 万 MAU/月 |
|---|---|---|
| LLM 对话（~30 次/天，~500 token/次） | ~¥0.5 | ~¥5,000 |

## 七、主动搭话怎么用记忆

机器人「克制地主动说话」，记忆在以下场景触发：

| 触发 | 记忆怎么用 | 示例 |
|---|---|---|
| 手机放回（唤醒） | 取 open 状态的未完成话题 | 「回来啦，面试准备得怎样了？」 |
| 间隔数天 | 取 importance 高且久未提及的事件 | 「上次说的那事后来怎么样了？」 |
| 情绪侧写疲惫 | 结合近期事件关心 | 「看你今天挺累的，面试的事还顺利吗？」 |
| 到提醒时间 | 读用户口头设定的提醒 | 「你说要我提醒你喝水的」 |

**约束**：

- 默认偏安静，同一话题不重复追问；
- 提供「话多/话少」开关；
- 深夜关灯不主动出声。

## 九、风险与对策

| 风险 | 对策 |
|---|---|
| LLM 记错（把朋友的事记成用户的） | 抽取时加 confidence，< 0.7 不入库；用户可在记忆中心修正 |
| 记忆太多 Prompt 装不下 | 第一期按 type 筛选 + importance 排序，取 Top 10；第二期再加向量检索 |
| 主动回访太烦 | 同一话题 ≥ 3 天间隔；默认关闭高频搭话；用户可关 |
| 手机离位记忆丢失 | 记忆存云端 PG，与手机无关；回位 API 直接读 |
| 用户隐私 | PRD 要求：记忆查看/清除入口；删除即真删 |
